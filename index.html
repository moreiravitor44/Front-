Testes no Front-end

Por que testar não é opcional

"Sem testes, você está apenas torcendo."

02 / 17

Código sem testes é código sem garantia

TypeScript garante que os tipos estão corretos — mas não garante que o comportamento está correto. A checagem de tipos não avisa se uma função utilitária retorna o valor errado, se um componente quebra ao interagir, ou se uma mudança de estado destrói um fluxo de trabalho.

O ponto central: a complexidade do front-end — gerenciamento de estado da UI, fluxos do usuário, orquestração de API, validação no cliente — torna os testes parte necessária de software de produção, e não um item opcional.

Tipos ≠ Comportamento

O compilador valida contratos, não regras de negócio nem efeitos colaterais.

Estado é frágil

Mudanças de estado disparam efeitos em cascata difíceis de prever sem verificação.

Usuário não segue o roteiro

Fluxos reais cobrem caminhos que nenhum desenvolvedor testou manualmente.

03 / 17

A Pirâmide de Testes

Uma estratégia saudável distribui os testes em camadas: muitos testes unitários, alguns testes de integração e poucos testes E2E.

Unitários

Mais numerosos. Mais rápidos, baratos e estáveis. Testam funções e componentes isolados.

Integração

Quantidade média. Velocidade média. Verificam a colaboração entre módulos e fronteiras.

E2E

Menos numerosos. Mais lentos e frágeis, mas validam caminhos reais do usuário.

Equilíbrio: testes unitários dão feedback rápido e barato; E2E dão confiança sobre a jornada completa — os dois são necessários, em proporções diferentes.
04 / 17

Testes Unitários — A Primeira Linha de Defesa

Testes unitários validam a menor unidade testável em isolamento. No front-end, uma "unidade" pode ser uma função pura, um método utilitário ou um componente de UI independente.

Bônus: testes unitários também forçam você a revisar a especificação — há lacunas? há ambiguidades? O teste expõe isso antes do usuário.

Onde brilham

Funções utilitárias, validações no cliente, transformação de dados, formatação, cálculo de estado derivado.

Onde não bastam

Fluxos completos do usuário, interações entre módulos, integração real com APIs e navegador.

05 / 17

Testes de Integração — Onde os Bugs Realmente Vivem

Testes de integração verificam a colaboração entre múltiplos módulos ou componentes. Muitos defeitos reais nascem exatamente nas fronteiras entre módulos.

Fronteiras

Uma atualização de estado dispara um efeito colateral errado.

Contratos

A validação do formulário e a lógica de envio se desencontram.

Compatibilidade

A saída do componente A tem um formato que o componente B não consome.

Vantagem: integração oferece cobertura mais realista que o unitário, ao mesmo tempo em que evita todo o custo do navegador. É a camada intermediária da pirâmide.
06 / 17

E2E — A Última Barreira

Testes End-to-End simulam ações reais do usuário: clicar em botões, preencher formulários, navegar entre páginas, e validar se a cadeia completa — da UI ao backend e ao banco de dados — funciona como esperado.

O que eles protegem: caminhos críticos do negócio — login, pagamento, fluxos centrais. São poucos, lentos e caros de manter, mas a confiança que oferecem nenhuma outra camada substitui.

Forças

Valida a jornada real do usuário, integra front + back + dados, detecta problemas de configuração e ambiente.

Custos

Lentos, mais frágeis e caros de manter. Devem ser reservados para os caminhos mais valiosos do produto.

Ferramentas

O ecossistema do front-end moderno

08 / 17

Ferramentas — Lado do Desenvolvedor

Vitest / Jest

Frameworks de testes unitários. Vitest tem suporte nativo a Vite/ESM; Jest tem ecossistema mais maduro, porém configuração mais pesada.

Testing Library

Testa componentes a partir da perspectiva do usuário (papéis, rótulos, texto), incentivando testes resistentes a refatoração.

Playwright

Framework E2E moderno, cross-browser, com espera automática e depuração avançada via Trace Viewer.

MSW

Mock Service Worker: intercepta requisições de rede no nível do service worker, com respostas consistentes.

SonarQube

Análise estática: detecta code smells, vulnerabilidades e gaps de cobertura antes da execução dos testes.

Cobertura

Istanbul / c8: medem cobertura de linhas, branches e funções — úteis como indicador, não como meta absoluta.

09 / 17

Ferramentas — Lado de QA

Cypress / Playwright

Automação moderna de UI Web. Amigáveis ao ecossistema JS/TS, com excelente experiência de depuração.

Selenium

Automação Web tradicional. Comunidade ampla e suporte a muitas linguagens, mas com custo de manutenção maior.

BrowserStack / LambdaTest

Nuvens de navegadores e dispositivos reais: cobertura de ambientes reais com execução paralela.

mabl / TestRigor

Ferramentas low-code / com IA: reduzem a barreira de scripts e atendem cenários de regressão intensiva.

Playwright

O padrão moderno para E2E

11 / 17

Playwright — Visão Geral

Playwright é o framework open-source de testes End-to-End da Microsoft, lançado em 2020. Ele automatiza ações reais do usuário — clicar, digitar, navegar — e espera que o elemento esteja interativo antes de agir, como "um usuário muito rápido".

Adoção: dados do StateOfJS mostram popularidade e retenção crescentes do Playwright na comunidade de desenvolvimento Web — hoje, uma das principais escolhas para E2E no front-end moderno.

Chromium

Motor do Chrome e do Edge.

Firefox

Motor Gecko, da Mozilla.

WebKit

Motor do Safari e iOS.

Dispositivos

Emulação de dispositivos e viewports.

12 / 17

Por que Playwright?

API unificada

A mesma API cobre Chromium, WebKit e Firefox, com emulação de dispositivos e modos headless e com interface.

Testes resilientes

Espera automática (sem timeout manual) e assertivas com retry eliminam a causa raiz de testes frágeis.

Isolamento

Cada teste roda em um BrowserContext independente: execução paralela e sem interferência entre testes.

Ferramentas do desenvolvedor

Codegen para gravação, Trace Viewer para depuração com "viagem no tempo" e integração profunda com o VS Code.

13 / 17

Playwright na Prática

Um teste de fluxo de login: os locators esperam automaticamente e as assertivas tentam novamente até o timeout — sem sleep manual.

test('fluxo de login', async ({ page }) => { await page.goto('/login'); await page.getByLabel('Email').fill('user@test.com'); await page.getByLabel('Senha').fill('segredo'); await page.getByRole('button', { name: 'Entrar' }).click(); await expect(page).toHaveURL('/dashboard'); await expect(page.getByText('Bem-vindo')).toBeVisible(); });
Boas práticas embutidas: locators baseados em papéis e rótulos (acessibilidade), espera automática e assertions resilientes a timing — três das maiores causas de testes instáveis desaparecem por padrão.
14 / 17

Playwright — Recursos Avançados

Codegen

Grava interações do usuário e gera código de teste automaticamente.

Trace Viewer

Depuração com "viagem no tempo": snapshots, logs, rede e console em cada passo.

VS Code

Extensão oficial: execução, depuração e geração de testes dentro do editor.

Network Mock

Intercepta e simula APIs com page.route().

Paralelismo

Testes isolados em BrowserContexts, com workers paralelos.

Dispositivos

Emulação de dispositivos reais, viewports e touch.

15 / 17

Testes no Pipeline CI/CD

O valor real dos testes automatizados cresce na integração contínua. Colocar testes unitários, de integração e smoke E2E no workflow de CI (GitHub Actions, Jenkins etc.) faz com que cada commit dispare a verificação — e o problema aparece antes do merge.

Orçamento de feedback: testes unitários dão feedback em segundos no watch local; integração termina em minutos no PR; smoke E2E serve de gate do PR, e a regressão completa pode rodar à noite.

Unit — Segundos

Watch mode local: ciclo de feedback quase instantâneo.

Integração — Minutos

Executada no PR, antes do merge.

E2E — Gate

Smoke no PR; regressão completa em execução noturna.

16 / 17

Como Escolher

Linguagem e framework

Vitest tem suporte nativo a Vite/ESM; Jest tem ecossistema mais maduro, mas configuração mais pesada.

E2E: Playwright primeiro

Cross-browser + espera automática + Trace Viewer formam, hoje, o conjunto mais equilibrado do mercado.

Comece pelos caminhos críticos

Não persiga 100% de cobertura E2E: proteja login, pagamento e CRUDs centrais.

Integração com CI

O Playwright fornece exemplos de configuração para os principais provedores de CI — adoção barata.

O Teste é Parte do Código

"Sem testes, você está apenas torcendo."

Unitários

Rápidos, baratos e estáveis — a primeira linha de defesa.

Integração

Capturam defeitos reais nas fronteiras entre módulos.

E2E — Playwright

Protegem caminhos críticos e dão confiança para o time lançar.

Testar é investir: cada camada existe para responder uma pergunta diferente — o unitário pergunta "este pedaço está correto?", a integração pergunta "estes pedaços conversam?", o E2E pergunta "o usuário consegue?".
